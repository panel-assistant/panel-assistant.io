同一仪表盘在手机或电脑上表现良好，廉价 Android 墙面板却可能反应迟缓、滚动卡顿、空白或停止更新。先检查 Home Assistant 发送给面板的工作量，再测量剩余的仪表盘与硬件限制，最后才考虑是否必须更换面板。

:::tip
常见原因是到达仪表盘的 Home Assistant 实体状态和更新数量。[竞速对比](/zh-hans/manage/drag-race/)通过并排拍摄两台相同面板展示其代价。大型安装可能迫使低功耗面板处理数千个从未显示的实体。使用[内置渲染器](/zh-hans/manage/built-in-renderer/)时，首先应尝试实体筛选。
:::

## 更改前先测量

在 Home Assistant 的面板设备页面使用**访问**打开 Web 界面（默认端口示例为 `http://<panel-ip>:8888/`）。每次变更前后，在相近时长内记录相同仪表盘视图，确保比较有意义。

- **仪表盘响应速度**：真实交互延迟、最慢交互的输入/处理器/呈现时间分解、主线程阻塞、可交互时间，以及意外渲染器重新加载。
- **Home Assistant 状态流**：每秒状态更新、未压缩 JSON 负载速率、初始状态填充大小、主线程让出执行权前的时间，以及过去一小时贡献最多的三个实体，分别按更新速率和负载量排名。
- **性能**和**资源占用最高的进程**：CPU、GPU、RAM、时钟频率、温度和最繁忙进程。
- **摄像头视频流**（提供摄像头的面板）：保持会话开启的订阅者、所用编码器、请求帧率与实际帧率，以及实际码率与编码器上限。实际速率明显低于请求时只报告事实，不附加原因：昏暗房间中的采集节奏、编码路径和视频硬件竞争都有可能，卡片不会猜测。请求绝不被悄悄降低；会话无法提供请求帧率时，卡片会同时显示请求值和给编码器的帧率。卡片有意不提供 CPU 数值，因为硬件编码同时在编解码硬件、合成器和应用中运行，没有哪个单一进程能代表摄像头代价。请从性能和占用最高的进程读取面板整体负载。
- **实体页面**：内置渲染器当前订阅内容、自动学习发现的内容，以及仍需决定的仪表盘规则。
- **诊断报告**（`/diag`）：原因仍不明确时可复制到问题报告的报告。

内置渲染器直接收集这些浏览器测量，无需 root 或 WebView 调试。使用独立仪表盘应用时，如果有 root 或辅助进程，面板应用可显示渲染器 CPU 和 Android 渲染数据，但不能测量该应用的真实交互延迟。

状态事件主线程指标从相关 Home Assistant 消息被分派开始，到浏览器执行完所有处理器和微任务并让出执行权结束。它包含面板应用少量观察开销，以及同一消息任务中的其他工作，因此有意不标为仅处理 Home Assistant 的时间。负载速率是前端处理的未压缩 JSON，而非压缩后的网络流量。

使用对齐图表寻找关联。交互峰值与繁重状态流量及状态事件占用重合，指向状态流规模问题。状态流安静时处理器耗时高，指向仪表盘 JavaScript。呈现延迟和长渲染帧指向布局、动画、摄像头或媒体工作。重复渲染器重新加载指向内存或渲染器不稳定。请综合读取测量；单次 CPU 快照无法单独确定原因。

**可能原因**行保守应用这些规则并报告置信度。证据不足以支持单一主要原因时，会明确说明。

### 从面板外比较过滤与未过滤状态

如果未过滤仪表盘使自身 WebView 过载，页面内数值可能停止变化。电脑上运行的采集脚本改为轮询面板应用自身性能接口，该接口属于已弃用 REST API（参阅[控制参考](/zh-hans/reference/api/#rest-api-已弃用)），因此整体面板 CPU 仍可观察；有 root 或辅助进程时，还可原生探测 Chromium 渲染器线程。它也记录最后一批浏览器测量的时间龄；超过 15 秒会报告为停滞，而非视为当前数值。

采集器不更改配置。它绝不会开启、关闭或重写实体筛选；首次请求可能在面板应用内部状态创建一个私有安装密钥。两次运行请选择相同仪表盘视图和工作负载，在面板 Web 界面更改筛选，等待仪表盘重新加载，然后在 [ha-paneld 仓库](https://github.com/panel-assistant/android)检出中，分别为两种状态运行命令：

```bash
python3 tools/measure-dashboard-performance.py collect --panel http://192.168.1.50:8888 --expect filtered --label filtered --output filtered.json
```

```bash
python3 tools/measure-dashboard-performance.py collect --panel http://192.168.1.50:8888 --expect unfiltered --label unfiltered --pair-with filtered.json --output unfiltered.json
```

比较结果：

```bash
python3 tools/measure-dashboard-performance.py compare filtered.json unfiltered.json --output comparison.json
```

每次运行默认三分钟，预热 30 秒，每 10 秒轮询。`--pair-with` 复用首次结果中的不透明比较 ID，使比较可拒绝不同实机、不同配置的 Home Assistant 或仪表盘，以及影响测量的设置变化，而不记录这些私有值。它无法检测同一仪表盘内手动选择了不同视图，因此请保持可见视图和工作负载相同。

预期模式未激活、筛选修订或渲染器代次变化、采集期间构建或配置改变、筛选回退，或保留的样本少于三个、整体面板 CPU 样本少于三个、原生渲染器 CPU 样本少于三个时，采集器会拒绝运行结果。它仍会写出被拒绝结果及准确原因，绝不覆盖现有输出文件。

JSON 不包含面板 URL 和 ID、Home Assistant URL 和仪表盘路径、实体 ID、进程名称或筛选哈希。面板使用永不离开本机的私有随机 256 位安装密钥计算不透明指纹，且指纹仅属于一对比较，因此不能关联不同测量或猜测面板名称。无法存储密钥的面板会拒绝测量。未过滤实体数是目录最后同步的数量，而非从过载 WebView 获取的实时数量；目录为空时报告不可用。网络和浏览器流量计数按实际观察间隔归一化，因此漏掉一次轮询不会扭曲比较。浏览器时序和流量速率过期时不计入摘要，但继续收集面板应用自身的 CPU、内存、网络和渲染器数据。

### 可选的远程 WebView 调试

内置性能卡片不需要 DevTools。只有需要深入检查页面源代码时，才使用**远程 WebView 调试**卡片。

对于独立仪表盘应用，请先开启该应用自身的 WebView 远程调试设置并重新启动仪表盘；否则中继无法找到其 WebView。网络中继本身需要 root。

### 排除原装 NSPanel Pro Zigbee 看门狗缺陷

较旧的 Sonoff NSPanel Pro 原装固件包含递归赋值 `export LD_LIBRARY_PATH=/vendor/bin/siliconlabs_host/:${LD_LIBRARY_PATH}`，可能使厂商的 `guard_process.sh` 本身成为性能问题。[社区调查](https://github.com/panel-assistant/android/issues/34)在运行原装固件 3.8.0 的 NSPanel Pro 120 上确认该缺陷，并报告其全部 16 台面板均受影响。脚本每五秒将目录添加到前面。约十小时后，环境字符串超过 Linux 启动程序的单字符串长度限制，外部命令开始以 `E2BIG` 失败，`sleep` 不再延迟循环，看门狗可能占满一个 CPU 核心。此时还可能无法重启已停止的 `zgateway`，导致 Zigbee 不可用。包含同一行的 1.x 到 3.x 固件可能受影响，但尚未独立验证。

原装 NSPanel Pro 空闲时周期性出现系统负载，可检查以下模式：

- `guard_process.sh` 持续接近一个 CPU 核心的 100%，进程大小远超健康状态约 9 MB；
- `zgateway` 缺失或不再恢复；以及
- 重启有帮助，但约十小时后负载再次出现。

重启只会暂时重置累积环境。链接问题包含报告者提供的 root 和 ADB 变通方法，项目尚未独立验证。除非厂商脚本中准确的递归赋值恰好出现一次，否则不要应用。任何修复都必须先验证非空备份，并保留所有者、权限模式和 SELinux 元数据。出现非预期匹配时应在更改前停止；更改后如果重启或验证失败，请回退，将 `/vendor` 恢复只读，并检查 `zgateway` 及其在 Home Assistant 中的可用性。重写 `/vendor` 的固件更新会移除本地补丁；只有新固件仍含该赋值时缺陷才重现。社区检查未在固件 4.0.12 和 4.6.0 中找到该行。

此缺陷不同于稳定的 `zgateway` 因无线模块不响应而忙循环。面板 Zigbee 健康传感器区分看门狗和网关 CPU、入网证据和重启历史。它会警告准确的递归赋值，但不会自行编辑厂商脚本。已配置网关明确未加入网络，并在 15 分钟宽限期后连续五个一分钟样本超过一个核心的 50% 时，会被自动关闭并限制影响；已入网路由器 CPU 高只会发出警告。

## 按影响程度排列的解决方法

### 1. 筛选内置渲染器的实体订阅

Home Assistant 前端通常订阅登录用户可见的每个实体状态。即使仪表盘只使用少数实体，面板也必须接收和处理所有状态。内置渲染器可将仪表盘学习到的实体集加入订阅，使 Home Assistant 在序列化和发送前过滤流。面板仍保持正常的已认证 Home Assistant 连接，无需代理或额外服务器。

实体筛选仅适用于内置渲染器。引导设置会在首次加载仪表盘前询问是否开启；已完成设置的面板：

1. 在 Home Assistant 面板设备页面使用**访问**，打开**设置**、**仪表盘**，选择**内置渲染器 (ha-paneld)**，开启**实体筛选**。
2. 打开**实体**标签页，选择**立即扫描仪表盘**。
3. 访问每个仪表盘标签页并使用控制、弹出窗口和条件内容，让运行时依赖有机会被观察到。
4. 检查当前、建议和排除的实体。固定自定义卡片或模板间接需要的实体。
5. 解决实体筛选检查。尽可能缩小宽泛或动态仪表盘规则，或明确选择并接受面板显示的警告。
6. 应用实体集，让仪表盘重新加载，使用仪表盘标签页的性能卡片比较相同视图。

自动学习无法证明自定义卡片或动态模板的所有依赖。缺少实体可能使卡片过期或不可用，因此请先在不依赖的面板上检查结果，在候选可信之前保持筛选关闭。未过滤订阅始终保留为恢复途径：关闭**实体筛选**并重新加载仪表盘。

旧学习证据或手动选择不再描述仪表盘时，使用实体页面的**重置已学习的数据**。确认后会清除学习成员、固定、排除和已忽略的安全决定，保留已知可用的当前筛选，并开始新扫描。重建候选期间，原筛选继续作为备用。

### 2. 减轻仪表盘本身负担

- 将密集仪表盘拆分为专注的视图，避免加载面板从不需要的卡片。
- 自定义卡片持续动画、构建大型文档树或频繁运行 JavaScript 时，优先使用内置卡片。
- 观察交互处理、长动画帧和渲染器重新加载。如果某个视图占主导，请简化它，或在寻找高开销卡片时用 `button.<panel>_reload` 临时恢复。
- 单独测试摄像头和图表卡片。即使实体筛选正常工作，其解码、历史查询和渲染仍可能占据主要负载。

### 3. 在来源减少不必要更新

实体筛选保护面板免受未显示实体的负担，但不会降低必需实体的代价。如果仪表盘确实显示电力计、蓝牙距离传感器、快速变化的模板或频繁更新的诊断实体，请在集成允许时降低来源更新速率。这也可减少整个 Home Assistant 安装的记录器和数据库工作。

有用控制包括 ESPHome 节流和变化量过滤器、Zigbee 报告间隔、集成 `scan_interval` 设置，以及降低模板更新频率。全面应用前，检查变更不会降低自动化或历史视图的实用性。

### 4. 让剩余仪表盘适配硬件

PX30 和 RK3566 面板能良好运行专注的仪表盘，但单线程性能仍有限，通常只有 2 GB RAM。实体筛选移除不必要状态工作，不能让过大摄像头流、复杂动画或大型历史图表变得没有代价。请按面板逻辑显示尺寸设计，并测试最重的视图，而非只看主页。[硬件页面](/zh-hans/hardware/)比较受支持的面板。

## 参考

### 为什么大型 Home Assistant 安装会拖慢面板

Home Assistant 前端保持 WebSocket 订阅，接收用户可用实体的当前状态及每次后续更新。不限制实体集时，渲染器收到的数据远超专注墙面仪表盘所需。JavaScript 主线程必须解析消息、更新前端状态模型，并判断可见内容是否变化。

低成本面板尤其敏感，因为 JavaScript、布局和绘制高度依赖一个渲染器线程。额外 CPU 核心有助于其他工作，但不能移除此延迟；RAM 有限时，随着 WebView 内存增长，垃圾回收的干扰越来越大。

### 常见症状

| 症状                                                                 | 可能原因                                               |
| -------------------------------------------------------------------- | ------------------------------------------------------ |
| 点击延迟、导航迟缓或滚动卡顿                                         | 大型实体流、高负载卡片或两者共同造成渲染器主线程工作   |
| 某个仪表盘视图远差于其他视图                                         | 该视图的高开销卡片、摄像头解码、历史数据或大型文档树   |
| 整个视图空白，但周围界面仍在                                         | WebView 内存压力或渲染器故障                           |
| 仪表盘数日内逐渐变差                                                 | 内存增长、碎片化或累积工作的卡片                       |
| 实体停止更新后突然成批到达                                           | WebSocket 中断、重连或渲染器无法跟上                   |
| 相似面板表现不同                                                     | 仪表盘内容、实体订阅、WebView 版本、运行时间或温度不同 |
| 原装 NSPanel Pro 启动约十小时后卡顿，`guard_process.sh` 占用一个核心 | 厂商 Zigbee 看门狗递归赋值导致 `E2BIG`                 |

垃圾回收会不时暂停 JavaScript 来回收未使用内存。接近内存上限时，暂停更长且更频繁，即使 Android 进程未崩溃，也可能使渲染得不到执行时间。
