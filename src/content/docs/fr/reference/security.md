ha-paneld exécute un agent de premier plan sur un panneau mural, exposant un service web local (port `8888` par défaut), un démon auxiliaire root et un relais CDP/DevTools facultatif. **Le mode Souple conserve par défaut l’association clé en main sans jeton et la confiance dans le réseau local.** Le [mode Renforcé](/fr/manage/security-mode/) facultatif exige un accès physique pour les requêtes LAN directes protégées. Certaines actions de gestion courantes peuvent passer par la barre latérale Panel Assistant authentifiée pour un administrateur ; les autres opérations protégées exigent toujours une approbation à l’écran du panneau. La barre latérale ne sert pas de proxy à l’interface web : elle affiche la page propre au panneau et relaie ses requêtes via sa session Home Assistant authentifiée, qui identifie l’administrateur. Il n’y a donc pas d’identifiant d’intégration distinct. Le service local restant sans authentification constitue un risque résiduel accepté ; la segmentation réseau est le contrôle plus large, et le modèle d’authentification Home Assistant est la voie retenue si une authentification générale est ajoutée. Cette page consigne le modèle de menace et les décisions prises.

## Modèle de confiance

Le panneau et Home Assistant se trouvent normalement sur un **réseau local de confiance**, et l’application est conçue autour d’une **association clé en main sans jeton**. Un attaquant disposant de root ou d’un accès aux fichiers du panneau est hors périmètre : il contrôle déjà l’appareil. Le logiciel déjà exécuté sur le panneau est aussi considéré comme fiable pour la frontière du mode Renforcé, car les requêtes de bouclage ne peuvent pas être attribuées sûrement à l’interface ha-paneld plutôt qu’à une autre application Android locale. Le mode Renforcé est une frontière facultative de présence physique pour les réseaux où tous les clients distants ne doivent pas pouvoir effectuer des opérations destructives ou portant des identifiants secrets ; ce n’est pas une couche complète d’authentification.

:::caution
Le **risque résiduel accepté** notable : un acteur du réseau local sans identifiants peut toujours atteindre des routes HTTP locales non authentifiées. Le mode Renforcé protège les opérations listées sur la [page des modes de sécurité](/fr/manage/security-mode/), avec une exception limitée pour la barre latérale administrateur authentifiée, mais n’authentifie pas toutes les lectures ou commandes courantes. La restriction d’accès reste déléguée à la segmentation réseau ([décision 2](#décisions)), avec l’authentification Home Assistant ([décision 3](#décisions)) comme voie retenue pour l’authentification générale.
:::

L’exposition se concentre sur les routes modifiant l’état du port HTTP du panneau :

- En mode Renforcé, une origine Home Assistant modifiée ne peut pas hériter de l’identifiant secret stocké pour l’ancien point d’accès : son remplacement doit arriver dans le même enregistrement, sinon l’ancien est effacé. Cet effacement s’applique dans les deux modes. Le changement de destination reste un risque de déni de service, car la configuration courante n’est généralement pas soumise à approbation.
- La lecture multimédia distante télécharge et lit une URL HTTP(S) arbitraire ; HTTPS utilise le magasin de confiance de la plateforme et la vérification normale du nom d’hôte, tandis que HTTP en clair reste disponible pour les sources LAN. Les requêtes multimédias distantes exigent une approbation physique en mode Renforcé.
- Le lancement du relais DevTools démarre le relais CDP (surface `:9222` ci-dessus) en mode Souple ; le mode Renforcé ferme et désactive cette surface au lieu de l’approuver.
- Les routes d’enregistrement/activation/retour arrière des profils peuvent changer les pilotes compilés et capacités candidates utilisés après un redémarrage contrôlé du service. Les jetons d’aperçu lient l’enregistrement au YAML exact inspecté, l’activation épingle une révision/empreinte exacte, les déclarations risquées sont mises en évidence et le démarrage revient à la dernière révision connue comme fonctionnelle. Activation et retour arrière exigent une approbation physique en mode Renforcé.
- `GET /diag` renvoie des informations sur l’appareil et ses capacités, utiles pour la reconnaissance. C’est volontairement un outil d’assistance.
- Les captures d’écran et l’injection d’entrées permettent de voir le panneau et d’y injecter des commandes. Les voies root/auxiliaire les exposent déjà ; le service d’accessibilité activé localement peut aussi fournir des touchers et, sur Android 11 ou ultérieur, des captures sans root. Le mode Renforcé conserve les captures mais refuse les entrées hors bouclage, empêchant un appelant distant d’actionner l’interface native d’approbation.
- L’installation de composants peut installer des versions ha-paneld ou minimales de l’application mobile Home Assistant au signataire épinglé. L’installation et la validation finale d’un APK téléversé inspecté sont protégées par le mode Renforcé.
- Les routes d’exportation et de restauration complètes peuvent transporter des secrets de configuration et, sur sélection explicite d’un panneau rooté ou avec auxiliaire, les fichiers autorisés de connexion à l’application mobile Home Assistant. L’approbation du mode Renforcé protège exportation réseau et restauration ; les archives `.hpb` chiffrées restent le format portable recommandé. L’auxiliaire n’a aucune commande générale de système de fichiers privé ; le transfert de connexion mobile est confiné par descripteurs, borné en taille et restauré transactionnellement.

Le service de gestion utilise HTTP en clair selon le modèle de confiance LAN. Requêtes protégées et données sensibles nécessitent un réseau fiable et segmenté ; le mode Renforcé ne chiffre pas le transport.

### Attaques par l’intermédiaire du navigateur

Elles sont protégées par [`OriginGuard`](https://github.com/panel-assistant/android/blob/main/app/src/main/kotlin/io/panelassistant/android/http/OriginGuard.kt) :

- **CSRF** : OriginGuard refuse une requête modifiant l’état (`POST`/`PUT`/`PATCH`/`DELETE`) dont l’`Origin`/`Referer` présent ne correspond pas au `Host` de la requête. Une page web LAN malveillante ne peut donc pas piloter silencieusement ces points d’accès. Les `fetch` de même origine et les clients API sans en-têtes (curl, `rest_command` Home Assistant) ne sont pas affectés.
- **DNS rebinding** : l’en-tête `Host` doit être une adresse IP littérale, `localhost`, `*.local` (mDNS) ou un nom configuré par l’opérateur (`http_allowed_hosts`) ; tout autre nom est refusé pour toutes les méthodes. Un attaquant reliant son propre nom DNS au panneau ne peut donc pas se faire passer pour la même origine afin de lire des secrets (exportation de configuration) ou piloter la surface. L’accès par IP, habituel, reste toujours autorisé et est intrinsèquement protégé du rebinding.

Chaque requête passe d’abord le contrôle de rebinding ; la suite dépend de sa modification d’état, de son lancement d’un travail privilégié ou de son caractère de simple lecture :

1. **Contrôle Host.** Une requête sans en-tête `Host` passe, car aucun nom ne peut être réaffecté. S’il est présent, `Host` doit être une IP littérale, `localhost`, `*.local` ou figurer dans `http_allowed_hosts`, sinon la requête est refusée.
2. **Méthodes modifiant l’état** (`POST`, `PUT`, `PATCH`, `DELETE`). Sans `Origin` ni `Referer`, la requête est autorisée comme client API LAN sans en-têtes. Si l’un est présent, il doit être analysable et son autorité égale à `Host` ; sinon elle est refusée comme écriture inter-origines.
3. **`GET` actifs** (démarrant capture, sous-processus, échantillonnage ou actualisation réseau). Un `Sec-Fetch-Site` valant `cross-site` ou `same-site` est refusé. Sinon, un `Origin` ou `Referer` présent passe le même contrôle d’analyse et de correspondance qu’une écriture. Sans les deux, une requête dont l’agent utilisateur ressemble à un navigateur mais sans Fetch Metadata est refusée ; les autres sont autorisées comme automatisation.
4. **`GET` ordinaires** : autorisés, car la politique de même origine du navigateur bloque déjà la lecture inter-origines de la réponse.

Trois de ces comportements peuvent facilement être mal interprétés. **L’absence de `Host` passe** le contrôle contre le rebinding. Une requête qui modifie l’état et comporte un en-tête `Origin` ou `Referer` mais aucun `Host` est refusée, tout comme une telle requête dont l’origine fournie ne peut pas être analysée. Les requêtes ne comportant aucun de ces deux en-têtes d’origine restent autorisées par ces protections. Les requêtes `GET` ordinaires ne font délibérément pas l’objet d’un contrôle d’origine ; c’est l’_effet de bord_ d’une écriture ou d’une lecture active qui doit être protégé. Quant aux requêtes `GET` actives, elles suivent une troisième voie fondée sur Fetch Metadata, qui refuse par défaut une requête présentant les caractéristiques d’un navigateur si elle ne fournit aucun élément positif attestant une même origine, tout en laissant fonctionner les automatisations sans en-têtes.

Aucune protection n’authentifie l’_appelant_. Le mode Renforcé peut exiger une approbation physique pour une opération protégée ; la décision 3 décrit la voie d’authentification générale des appelants.

Les téléchargements d’APK via [`AppInstaller`](https://github.com/panel-assistant/android/blob/main/app/src/main/kotlin/io/panelassistant/android/util/AppInstaller.kt) imposent HTTPS : l’URL initiale et chaque redirection doivent être `https`, comme défense supplémentaire aux contrôles après téléchargement du signataire et du paquet, qui bloquent déjà un APK substitué.

Les fichiers de profils à l’exécution sont des données non fiables, pas des extensions. Le schéma fermé ne sélectionne que des pilotes compilés dans ha-paneld ; il ne transporte ni commandes shell, verbes d’auxiliaire, code natif ni scripts généraux. Les chemins privilégiés sont limités aux listes d’autorisation du cœur ; les métadonnées d’artefacts WebView ne sélectionnent que des identifiants gérés par le cœur dont l’URL HTTPS, la version, la somme de contrôle et l’empreinte du signataire sont compilées dans l’application. En 1.0.0-rc2 non publiée, une mise à jour lancée par le propriétaire utilise ces artefacts vérifiés uniquement si le fournisseur installé, le signataire, la version Android, l’ABI et la voie d’installation sont compatibles. Les paramètres de pilote sensibles sont validés par leur pilote propriétaire ; les déclarations ne remplacent jamais les sondes root/auxiliaire ou matérielles en direct.

## Décisions

1. **Aucun jeton API spécifique.** Un secret par panneau est jetable et nuit à la simplicité de configuration. (Rejeté.)
2. **Aucune liste réseau d’autorisation dans l’application.** Restreindre _qui_ atteint le port HTTP du panneau relève du réseau (routeur, VLAN ou segmentation par pare-feu) plutôt que d’une réinvention dans l’application, conformément à l’utilisation des capacités de plateforme et d’infrastructure existantes. La liste IP d’autorisation et `ip_ban` de Home Assistant protègent son serveur HTTP, pas le service HTTP distinct du panneau ; ils ne s’appliquent donc pas ici. La segmentation réseau est le contrôle existant. La voie applicative, si justifiée, est le modèle d’authentification Home Assistant (décision 3).
3. **Aucune authentification générale des appelants.** L’application n’authentifie pas les appelants LAN ; le modèle de confiance ci-dessus et le mode Renforcé sont les contrôles.
4. **Le chiffrement des identifiants au repos est hors périmètre.** Un attaquant root ou disposant des fichiers du panneau contrôle déjà l’appareil.
5. **La lecture multimédia conserve la vérification HTTPS standard tout en permettant HTTP en clair** pour les sources audio LAN selon le modèle de confiance LAN.
6. **Le mode Renforcé est facultatif et local à l’appareil.** Le mode Souple reste celui par défaut afin que les procédures Home Assistant et outils gérant plusieurs panneaux n’acquièrent pas d’invites sans surveillance. L’approbation renforcée est locale au processus, liée au pair HTTP et à la requête protégée exacte, valable dix minutes et consommée par une seule nouvelle tentative correspondante. Elle ne peut pas être activée par requête réseau, sauvegarde, restauration ou opération sur plusieurs panneaux, et ne peut coexister avec ADB TCP classique, des écoutes ADB persistantes ou explicitement adressées, le débogage sans fil Android ou le relais LAN d’outils de développement WebView. L’entrée est refusée par sécurité tant que ces voies de commande distante ne sont pas vérifiées inactives. L’injection de touchers hors bouclage est indisponible tant que le mode est actif. Les logiciels locaux déjà exécutés sur le panneau restent fiables. Le mode Renforcé couvre exportation/restauration portant des identifiants secrets, modifications logicielles et de paquets dont un téléchargement lié à une URL exacte, activation de profils, redémarrage, maintenance écran et moteur de rendu, récupération de base de données et médias distants. L’activation caméra via son entité Home Assistant exige une approbation sur le panneau dans les deux modes ; Configurer est un réglage distinct du propriétaire.
